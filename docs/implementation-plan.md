# Implementation Plan

## Product target

GradReach is a local research and outreach assistant for 2027 international MSc applications. It targets the countries configured in the ignored private profile and supports scholarship and low-tuition routes. Its research target is 200 candidates/programs. It records official-source evidence, keeps unknowns explicit, prepares reviewed drafts, and plans no more than five outreach attempts per calendar day in the configured timezone.

The applicant profile, credentials, grades, English-test status, funding needs, and document references remain configurable private inputs. The repository must not invent those facts or publish them.

## Implemented behavior and boundaries

### Discovery and assessment

Phase 3 uses reviewed exact-host HTTPS allowlists and refuses redirects or pages outside the listed host. Search queries target faculty, professors, supervisors, labs, and research groups. Brave and official-page failures expose only sanitized categories and safe HTTP status/resource paths; raw errors, response bodies, credentials, and profile-derived search queries are omitted from failure records. Failure categories distinguish timeout, DNS/TLS, HTTP status, rate limit, rejected redirect, disallowed host, invalid content, and other network failures. The bounded historical pilot made one request capped at three results per then-configured region; five searches produced 12 leads. The Thailand retry returned HTTP 422 with the same three-result limit. The initial safe page-fetch workflow added dated, exact-host excerpts for nine leads and copied 42 relevant literal sentence snippets. Of three failed lead pages retried once, both China retries succeeded and the Italy retry returned HTTP 404. The retries added 11 further literal snippets, for 53 total; their source URL, retrieval time, and supporting excerpt are retained. The Italy lead now points to a current official Computer Science and Engineering page; its former failed URL remains in retry history. The next one-request-per-country pilot for Japan, South Korea, the United States, and New Zealand used a three-result cap and failed with sanitized `network_error` for each country; no request was retried and no leads were returned. Captured excerpts did not explicitly support a professor name or email address, so none was extracted. Search and page evidence remains unverified and review-gated. Pilot results are local in ignored `outputs/phase3-search-pilot.json`; active allowlist sources and check dates are in [phase-3-allowlist.md](phase-3-allowlist.md). Each country is eligible for discovery only after its exact official host is documented. Fixture tests cover query shaping, host validation, redirects, normalization, deduplication, failure classification, and review gating. The Brave adapter uses `SEARCH_PROVIDER_API_KEY`.

On 2026-10-31, eight fresh one-request pilots (South Korea, Australia, Canada, China, Italy, Portugal, Switzerland, and Belgium) used the exact-host allowlist and a three-result cap. All 24 returned items failed the save gate: one duplicate, 20 validation rejections, and three official-page fetch failures; no lead was saved. Exact-host mismatches were recorded for some results; no mismatched host was added without official evidence. The South Korea fetch failure was the safe path `/ci_mail/www/email/subscribe` with HTTP 500. Inspection found the link classifier treated any `email` path as a contact page, including subscription routes; the classifier now skips newsletter/subscription links, with a regression test proving that an optional subscription page cannot block a qualifying same-page professor profile. The Belgium results included two 302 responses on the allowlisted host; those redirects were rejected and not followed. The generalized runner accepts one `--region` value only when it is both in the current profile scope and exact-host allowlist, and performs at most one request.

The exact host `eng.kuleuven.be` is documented for Belgium from KU Leuven's official Computer Science master's page. The country audit now records exact hosts and faculty-directory evidence for 42 of 45 configured countries; no bulk or parent-domain allowlisting was used. Source-by-source additions and the three uncovered countries are recorded in [phase-3-allowlist.md](phase-3-allowlist.md).

### Directory traversal follow-up (2026-11-09)

The Canada pilot's directory result exposed a traversal weakness: a page with roughly 100 same-host links yielded only three fetched links and no confirmed professor. Traversal now ranks at most 100 same-host candidates using deterministic anchor text, profile URL shape, faculty-card context, and academic-role signals, and selects at most the top 10 for a directory. Student, admin, news, contact, login, and directory-navigation links are filtered. A shared 30-page fetch budget caps the whole discovery run, including search-result pages and linked research pages. Identity requires a plausible individual name on the official page plus an academic role; a directory label or search snippet cannot establish identity. Research pages are considered only after identity, remain exact-host checked, and must pass the existing saved-interest evidence gate. Selection diagnostics retain bounded ranks, controlled reason codes, and link counts without page text, search queries, interests, or credentials.

Offline fixtures cover prioritization after unrelated links, the per-directory and run-wide caps, navigation and exact-host filters, role-less identity rejection, and the directory → named profile → linked research path. The prior Canada pilot proves only that its then-current traversal fetched three directory links without establishing a person; it does not evaluate the new ranking. The requested post-change Canada pilot was not run: `npm run discovery:preflight` returned `{ok:false, profilePreferencesRead:false, denmarkConfigured:false, leadIdsRead:false, failureKind:"network_error"}`. Pilot verification is blocked until that preflight can read the configured database/profile state. No extra host was added.

New result processing keeps the search region separate from a person's country and leaves institution/country blank until official evidence can supply them. A result becomes `professor_profile` only when the exact fetched allowlisted page has a plausible person heading and a substantive research sentence; that literal sentence and source URL are retained on the same unreviewed evidence item. Generic school, program, and research-area pages keep their own lead types. Official email is stored only when an allowlisted page has a `mailto:` address in a semantic block that explicitly names that person; no address is inferred. These checks are deliberately conservative HTML heuristics: they can miss unusual layouts and do not establish current employment, affiliation, location, or research-fit approval. Search evidence, page evidence, email, and profile classification remain unreviewed until a person reviews them. The local triage gate still requires an exact profile quote that matches configured research interests before it can recommend likely relevance.

The first live professor-profile pilot was capped at one Brave request and three results. Its single request failed with sanitized `network_error` before any result diagnostics or leads were saved. The local MongoDB SRV lookup also timed out, so no canonical candidate records were changed; no request was retried. No real professor profiles were found in this pilot.

On 2026-10-31, the two legacy discovery collections were renamed in place to `discovery_leads` and `lead_triage_recommendations`. Read-only verification found 11 lead documents and 11 triage documents after the rename, with the `_id_` index retained on each collection. The legacy leads have no saved lead type or separate professor name, so the review viewer lists them under general or unclassified leads; page titles are not treated as professor identities. The candidate model now stores page/lead title separately from `professorName`, which is set only from supported official profile evidence or explicit evidence review. No Brave or Gemini request was made during this update.

Phase 4 validates reviewed program JSON and keeps unsupported facts unclear. GPA and currency scales are never converted. Affordability is only compared when annual budget and currency are configured. Transcript references can remain in the private profile; transcript parsing is not implemented. Program, assessment, and scheduler repositories/indexes exist. Their MongoDB integration test is skipped without `MONGODB_TEST_URI`. Do not substitute `MONGODB_URI` unless it is deliberately configured as a disposable test deployment.

### Draft generation

The deterministic draft template and optional `GeminiDraftProvider` use only inputs explicitly supplied by the caller. Choosing the Gemini dashboard draft option sends the candidate/applicant names, degree, target interest/intake, selected verified excerpt, and source URL to Google's Gemini API; transcript and CV contents are not sent. The separate evidence-triage option sends configured research criteria plus at most two sanitized excerpts from exact allowlisted HTTPS official-page sources for each of at most 11 leads; a candidate name is sent only for a named professor profile. It excludes applicant details, transcript/CV data, search queries, and contact evidence. General school, department, and program pages remain discovery evidence and yield an uncertain recommendation. A likely-relevant recommendation requires a profile that explicitly identifies the professor and substantive research or lab work matching a configured research interest. Each stored rationale is generated from validated evidence categories, and its supporting fact quotes must exactly match the saved excerpt and source URL. Previously saved triage records are not automatically rewritten; they retain their existing values until a later triage run applies this gate. Recommendations are stored in `lead_triage_recommendations`, separate from candidate review, approval, and email state. Triaged records remain advisory and do not approve or send anything. `LLM_PROVIDER_API_KEY` and optional `LLM_PROVIDER_MODEL` configure the shared adapter. No model output approves or sends a message.

### Gmail and outreach

`beginGmailAuthorization` runs a loopback callback with random OAuth state and PKCE. It requests only `https://www.googleapis.com/auth/gmail.send`; it does not request inbox or mailbox access. It requires a refresh token before saving authorization, so the polling worker cannot appear connected with a short-lived access token only. Tokens go to `EMAIL_PROVIDER_TOKEN_PATH` or the ignored default `private-data/gmail-token.json`; Windows applies a current-user-only file ACL, and other platforms use mode `0600`. The client ID/secret are read from `EMAIL_PROVIDER_CLIENT_ID` and `EMAIL_PROVIDER_CLIENT_SECRET`.

`GmailDeliveryService` remains disabled unless `OUTREACH_SENDING_ENABLED=true`. It delivers only a saved draft whose exact content fingerprint was approved, whose official profile/contact/program evidence remains reviewed, and whose recipient matches the queued address. Mongo claims audit rows atomically, records attempts and provider IDs, reserves the five-message limit atomically per configured local date, blocks while paused, retries only definitive retryable failures (up to three attempts), and marks uncertain outcomes without automatic resend. Queue creation is idempotent by candidate and scheduled instant. The `npm run outreach:scheduler` worker polls once per minute; by default it exits before connecting to MongoDB. Tests now verify that disabled or unset configuration cannot start a database connection. Keep the opt-in false during local authorization and review. The owner reports Gmail authorization is connected; no live message was sent or verified. Pause takes effect for future delivery claims; an already in-flight provider request may complete.
